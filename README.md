# Title: Aster – LangGraph Agent with Tools, Intent Routing & Memory

# Aster — Minimal LangGraph Agent (Streamlit GUI)

Aster is a compact, production-oriented conversational agent built with **Streamlit** and **LangGraph/LangChain** concepts. It demonstrates core patterns for Retrieval-Augmented Generation (RAG), tool-enabled agents, and practical conversational engineering — all in a small, modular codebase.

---

## Highlights / What it does

* Streamlit chat UI with history, model controls, and memory controls.
* LangGraph-based agent pipeline (inject system → classify → route → execute → summarize).
* Intent routing: `tools` | `chat` | `clarify`.
* Two deterministic tools included: `calculator` and `current_time` with safe input handling.
* Rolling LLM-generated summaries stored in a Pinecone vector index (persistent semantic memory).
* Retrieval of relevant memory blurbs on each turn to implement RAG (retrieve → augment prompt → generate).
* Tool-call traces and tool results shown inline for explainability.

---

## Architecture (textual diagram)

```
User (Streamlit chat UI)
        │
        ├─ Sidebar controls (model, prompt, temperature, memory)
        │
        └─ Chat input → st.session_state.agent_state.messages
                      ↓
                  StateGraph (LangGraph)
    START → inject_system → classify → [tools_agent | chat_agent | clarifier] → summarize → END
                      ↑
   - inject_system: prepends SystemMessage with persona + rolling summary + retrieved memory
   - classify: uses LLM structured output to choose route ("tools"/"chat"/"clarify")
   - tools_agent: lets the model call bound tools (calculator, current_time) up to N loops,
                 creates AIMessage, ToolMessage, final AIMessage
   - chat_agent: normal LLM response
   - clarifier: asks one clarifying question
   - summarize: updates short rolling summary (LLM) and stores it in Pinecone
                      ↓
                 Graph returns new messages (AI/Tool) → render_new_messages()
                      ↓
                Streamlit displays messages, tool traces (expanders), tool results
                      ↓
                Persistent memory: PineconeVectorStore (summaries + metadata)
```

## Quickstart

1. Clone the repository.
2. Create a Python virtual environment and install dependencies:

```bash
python -m venv .venv
source .venv/bin/activate  # or .venv\Scripts\activate on Windows
pip install -r requirements.txt
```

3. Set environment variables (or use a `.env` file):

```bash
export OPENAI_API_KEY=your_openai_key
export PINECONE_API_KEY=your_pinecone_key
export PINECONE_ENVIRONMENT=your_pinecone_env
# optional
export PINECONE_INDEX=langgraph
export PINECONE_NAMESPACE=summary-memory
```

4. Run the app:

```bash
streamlit run advanced_agent_v3.py
```

**Notes:** If you don't have Pinecone, you can run a simplified version using a local list/FAISS; the repo includes a `simple_aster.py` demo that runs without external vector DB.

## How this demonstrates RAG, tool integration, and conversational engineering

* **RAG-style memory:** Summaries are generated by the LLM, stored as embeddings in Pinecone, and retrieved as short blurbs to augment the system prompt. This is the canonical retrieve→augment→generate loop.
* **Tool integration:** The agent binds deterministic functions (`calculator`, `current_time`) as tools the LLM can call. Tool calls are executed by the runtime and returned to the LLM for further reasoning and a final response.
* **Conversational engineering:** The pipeline enforces persona injection, intent classification, context trimming (to avoid prompt bloat), rolling summaries, and explainability (tool traces). These patterns improve reliability and maintainability of LLM-driven conversations.

## Security & privacy

* Do **not** store PII in Pinecone without encryption and consent.
* Validate all tool inputs (the `calculator` shows a simple example).
* Sandboxing required for any tool that executes arbitrary code or calls external systems.
* Use least-privilege API keys and avoid committing `.env` files to VCS.

## Added persistent memory

🧠 What is Persistent Memory (Chroma)?

Normal LangGraph memory in your agent = short rolling summary (only keeps the last few turns).

Persistent memory with Chroma = long-term memory stored on disk so your agent can recall things even after you stop and restart the app.

It works like this:

After each turn, you take a summary, fact, or preference and embed it (turn into a vector).

Store that vector + the text in ChromaDB (a local vector database).

Later, when the user asks something new, you query Chroma to fetch relevant old info → inject it into the system prompt.

So persistent memory ≈ “a searchable notebook” of past conversations.

🗂️ Where is it stored?

By default, in a folder on disk (e.g. ./.arbii_memory/).

Inside that folder, Chroma manages SQLite + Parquet files that hold vectors and metadata.

## TL;DR Summary

You built a Streamlit chat app powered by a LangGraph state machine.

Every user turn:

1- A fresh SystemMessage is injected with the system prompt, a rolling summary, and retrieved Chroma memories relevant to the latest user message.

2- An intent classifier routes to: tools, chat, or clarify.

3- Tools (calculator/time) are orchestrated safely for up to 3 call rounds.

4- The turn is summarized and that short summary is persisted into Chroma for future retrieval.

- The UI shows:

chat bubbles,

tool-call traces,

a persistent memory panel (queryable, count shown, wipe button).

- All state (messages, intent, summary) lives in AgentState; UI rendering uses a separate chat_log for clean display.
